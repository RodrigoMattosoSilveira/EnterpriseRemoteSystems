Proposed top-level authorization profiles
APPLICATION_ADMIN

Global scope.

Can create, read, and update records across all tenants.

This should be rare and probably reserved for system operators or super-admins.

TENANT_ADMIN

Tenant scope.

Can create, read, and update all records inside their own tenant only.

This is the main tenant owner/admin role.

EARNINGS_OPERATOR

Tenant scope.

Can work with collaborator visibility, planning, and earning-posting workflows, but should not automatically get broad expense or settlement authority.

EXPENSE_OPERATOR

Tenant scope.

Can work with collaborator visibility, price lists, current account summaries, expenses, and receipt workflows, but should not automatically get planning or earning-posting authority.

Suggested permission groups

I would model the permissions something like this:

tenants.read
tenants.create
tenants.update

people.read
people.create
people.update

collaborators.read
collaborators.create
collaborators.update

planning.read
planning.create
planning.update

earnings.read
earnings.create
earnings.update

price_lists.read
price_lists.create
price_lists.update

expenses.read
expenses.create
expenses.update

current_accounts.summary.read
current_accounts.ledger.read
current_accounts.ledger.create

ledger.receipts.read
ledger.receipts.create
ledger.receipts.print
ledger.receipts.return
ledger.receipts.backfill

Then later settlement/correction permissions remain separate:

ledger.corrections.create
journey.settlements.preview
journey.settlements.zero_gold
journey.settlements.partial_payout
journey.settlements.close

That separation matters because “current account summary read” is much safer than “create ledger movement” or “close journey.”

Role-to-permission mapping

A first draft mapping could be:

Profile	Scope	Grants
APPLICATION_ADMIN	all tenants	all permissions
TENANT_ADMIN	own tenant	all tenant-scoped permissions
EARNINGS_OPERATOR	own tenant	collaborators.read, planning.read/create/update, earnings.read/create, maybe current_accounts.summary.read
EXPENSE_OPERATOR	own tenant	collaborators.read, price_lists.read/create/update, current_accounts.summary.read, expenses.read/create, ledger.receipts.read/create/print/return

I would be cautious with this one:

Expenses can CR his tenant collaborators' receipts

For receipt operations, I’d split it into:

ledger.receipts.read
ledger.receipts.create
ledger.receipts.print
ledger.receipts.return
ledger.receipts.backfill

The reason is that backfill is operationally powerful and should probably belong to TENANT_ADMIN or APPLICATION_ADMIN, not a normal expense operator.

Important clarification: tenant scoping must be mandatory

For every non-application actor, authorization has two checks:

1. Does the actor have the required permission?
2. Is the target record inside the actor’s tenant?

So EXPENSE_OPERATOR with expenses.create can create an expense only for a collaborator in their own tenant.

That means the future authorization service should not stop at:

RequirePermission(actor, PermissionExpensesCreate)

It will also need tenant-aware checks like:

RequireTenantAccess(actor, targetTenantID)

or a combined form later:

Authorize(ctx, actor, PermissionExpensesCreate, Resource{
    TenantID: expenseTenantID,
})

PERSON

Scope: own records only.

A PERSON actor can read only data that belongs to them directly, or to their linked collaborator/current journey.

Suggested permissions:

people.self.read
people.self.update

collaborators.self.read

current_accounts.self.summary.read
current_accounts.self.ledger.read

assignments.self.current.read

ledger.receipts.self.read

For your exact requirements:

Requirement	Suggested permission
RU his Person record	people.self.read, people.self.update
R his Collaborator record	collaborators.self.read
R his current account records and summary	current_accounts.self.summary.read, current_accounts.self.ledger.read
R his current assignment	assignments.self.current.read
R his current receipts	ledger.receipts.self.read

Important distinction: these are self-scoped permissions, not tenant-wide permissions.

So this actor should not get:

people.read
collaborators.read
current_accounts.summary.read
ledger.receipts.read

Those imply broader tenant visibility.

The eventual authorization check should be something like:

RequirePermission(actor, authz.PermissionPeopleSelfRead)
RequireSelfPersonAccess(actor, personID)

or later as one combined resource-aware check:

Authorize(actor, authz.PermissionPeopleSelfRead, authz.Resource{
    TenantID: tenantID,
    PersonID: personID,
})

For receipts, the check should prove that the receipt belongs to the person’s own linked collaborator journey before allowing read access.

# Ahthz
An authz actor is the application’s authorization-side representation of “who is trying to do something.”

It is not exactly the same thing as a Person, Collaborator, or future login User. It is the security identity used by authorization checks.

In ERS terms, an actor answers:

Who is making this request?
Which tenant are they acting in?
What permissions do they have?
Are those permissions global, tenant-scoped, or self-scoped?

Why have an actor concept?
Because many different real-world identities may need to act in the system:

Application administrator
Tenant administrator
Earnings operator
Expense operator
Person/self-service user
Temporary backfill operator
Future API/service account

Those identities do not all map cleanly to the same business table.

For example:

Person

means a human business record: CPF, RG, phone, address, bank info, emergency contact.

Collaborator

means a person participating in a collaborator journey.

Authz actor

means an authenticated/authorized identity capable of making application requests.

A person can have an actor, but a person is not automatically an actor. A system admin actor might not be a collaborator. A backfill/service actor might not be a person at all.

Actor versus role versus permission

Think of it as three layers.

Actor

The subject making the request.

Example:

actor_id = maria-expenses
tenant_id = tenant-abc
Role

A named bundle of permissions.

Example:

EXPENSE_OPERATOR
TENANT_ADMIN
PERSON
Permission

A specific allowed action.

Example:

expenses.create
ledger.receipts.return
current_accounts.summary.read
people.self.update

So the flow is:

Actor → has role grants → roles grant permissions → endpoint checks permission

Example:

Maria is an authz actor.
Maria has EXPENSE_OPERATOR for tenant ABC.
EXPENSE_OPERATOR grants expenses.create and ledger.receipts.return.
Maria may create expenses and record returned receipts for tenant ABC.
Why not just check the role directly?

Because endpoint code should avoid asking broad questions like:

IsExpenseOperator(actor)

It should ask precise questions like:

RequirePermission(actor, PermissionExpensesCreate)

That is more flexible. Later, if you decide that TENANT_ADMIN and EXPENSE_OPERATOR can both create expenses, the endpoint does not change. You only update role grants.

This is better:

RequirePermission(actor, authz.PermissionLedgerReceiptsReturn)

Than this:

if actor.Role != "EXPENSE_OPERATOR" && actor.Role != "TENANT_ADMIN" {
    return forbidden
}
Tenant-scoped actors

Most ERS actors should be tenant-scoped.

Example:

actor_id = joao-expenses
tenant_id = tenant-a
role = EXPENSE_OPERATOR

This actor may have:

expenses.create
ledger.receipts.return
current_accounts.summary.read

But only for records belonging to tenant-a.

So authorization is not just:

Does the actor have expenses.create?

It is:

Does the actor have expenses.create?
Is the target collaborator/expense/receipt in the actor’s tenant?

That second part is crucial.

For example, an expense operator for Tenant A must not be able to create an expense for a collaborator in Tenant B, even if they have expenses.create.

Global actors

APPLICATION_ADMIN is different.

That actor can act across tenants.

Conceptually:

actor_id = app-admin-rodrigo
scope = global
role = APPLICATION_ADMIN
permissions = *

This actor can operate across all tenants. It should be rare, audited, and not used for normal day-to-day tenant operations.

Self-scoped actors

The PERSON profile you added is different from both tenant-scoped operators and global admins.

A person actor should not be able to read all people in their tenant. They should read/update only their own person record and related records.

Example:

actor_id = person-123
person_id = person-123
tenant_id = tenant-a
role = PERSON

They may have:

people.self.read
people.self.update
collaborators.self.read
current_accounts.self.summary.read
current_accounts.self.ledger.read
assignments.self.current.read
ledger.receipts.self.read

But each check must prove ownership.

For example:

Can this actor read person_id = person-123?
Yes.

Can this actor read person_id = person-456?
No.

That means self-service permissions need both:

permission check
ownership check
What should be inside authz.Actor?

A practical ERS actor should eventually carry something like:

type Actor struct {
    ID          string
    TenantID    string
    PersonID    string
    IsGlobal    bool
    Permissions map[Permission]bool
}

Maybe later:

type Actor struct {
    ID          string
    TenantID    string
    PersonID    string
    Email       string
    DisplayName string
    IsGlobal    bool
    Roles       []string
    Permissions map[Permission]bool
}

But endpoint code usually should not care about roles. Roles are how permissions are granted. Permissions are what code checks.

Example: receipt return

For Bite 18B, receipt return is protected by permission:

ledger.receipts.return

The future full check should be:

1. Extract actor from request.
2. Resolve persisted roles/grants.
3. Confirm actor has ledger.receipts.return.
4. Load receipt/ledger entry/collaborator journey.
5. Confirm resource tenant matches actor tenant, unless actor is global.
6. Record receipt return.
7. Audit actor ID.

That prevents an expense operator from Tenant A from returning receipts for Tenant B.

Example: person self-service

For a person updating their own record:

PUT /api/v1/people/:id

The future check could be:

1. Actor has people.self.update.
2. Actor.PersonID == route person ID.
3. Actor.TenantID == person.TenantID.

For tenant admin updating a person:

1. Actor has people.update.
2. Actor.TenantID == person.TenantID.

Same endpoint, different authorization path.

How this relates to authentication

Authentication answers:

Are you who you claim to be?

Authorization answers:

Given who you are, are you allowed to do this?

ERS is currently building authorization first using temporary headers and persisted grants. Later, when real login/session/JWT support is ready, authentication will produce the actor identity.

Eventually:

JWT/session → actor ID → persisted grants → authz.Actor → permission checks

The temporary headers are just a bridge.

Recommended mental model for ERS

Use this model:

Person = business identity
Collaborator = journey/work/accounting identity
Authz Actor = security/request identity
Role = named permission bundle
Permission = specific allowed operation
Grant = role assigned to actor within a scope
Scope = global, tenant, or self

That separation will keep the app flexible as you add admins, operators, collaborators, self-service users, and maybe service accounts later.

# Overall
Why I choose this authorization model insteal of a JWT based one?

## Introduction

I did not choose this model instead of JWT. I chose it as the authorization model underneath JWT.

JWT is primarily an authentication/session transport mechanism. It answers:

```
Who is making the request, and did they present a valid signed token?
```

Authorization still needs to answer:

```
What is this actor allowed to do, in which tenant, on which resource?
```

So the intended end-state is not:

```
Headers forever instead of JWT
```

It is:

```
JWT/session → actor ID → persisted authz grants → authz.Actor → permission checks
```

## Why not put all permissions directly in the JWT?

You can, but for ERS I would avoid making JWTs the source of truth for permissions.

If a JWT contains all roles/permissions, then permission changes do not fully take effect until the token expires or is revoked. That is risky for financial/accounting operations like receipt returns, ledger corrections, payouts, zero-gold, and journey close.

For ERS, I prefer:

```
JWT contains identity claims:
- actor_id
- maybe tenant_id
- issuer/audience/expiry

Database contains authorization truth:
```
- actor active/inactive
- tenant scope
- role grants
- permission grants
```

Then each protected request resolves the current permissions from persisted grants.

That gives you immediate revocation:

```
Remove role grant → next request is denied
Deactivate actor → next request is denied
Change tenant scope → next request respects new scope
```

# Why use temporary headers now?

Because the app does not yet have full login/JWT/session infrastructure in place. The temporary headers are a bridge:

```
X-Authorized-By
X-Actor-ID
X-Tenant-ID
X-Actor-Permissions
```

They let us build and test authorization before authentication is finished.

But the direction should be:

```
Temporary headers: development bridge
JWT/session: future authentication carrier
Persisted grants: durable authorization source
```

# Why the actor model still matters with JWT


Even with JWT, you still need an internal actor object.

A future JWT might say:

```json
{
  "sub": "authz-actor-123",
  "tenant_id": "default",
  "exp": 1781234567
}
```

The backend would then do:

```go
actor, err := authz.ResolveActorFromJWTClaims(...)
```

And produce the same internal shape:

```go
authz.Actor {
    ID: "authz-actor-123",
    TenantID: "default",
    Permissions: ...
}
```

The endpoint should not care whether the actor came from:

```
temporary headers
JWT
session cookie
service account token
admin CLI
```

It should only care:

RequirePermission(actor, authz.PermissionLedgerReceiptsReturn)
RequireTenantScope(actor, targetTenantID)

That separation keeps authorization testable and avoids rewriting endpoint code when authentication changes.

## Why persisted grants are especially important for ERS

ERS has multi-tenant, financial, and self-service authorization needs:

```
APPLICATION_ADMIN: all tenants
TENANT_ADMIN: own tenant
EARNINGS_OPERATOR: planning/earnings only
EXPENSE_OPERATOR: expenses/receipts/current account summary
PERSON: own records only
```

These are not just “logged in or not logged in” decisions. They require:

```
tenant scope
role grants
permission grants
self ownership checks
auditable decisions
immediate removal of access
```

A JWT can carry the identity, but the database should decide whether the identity currently has access.

## Recommended final architecture

The final ERS model should be:

```
1. User logs in.
2. Backend issues JWT/session.
3. JWT contains actor identity, not full authorization truth.
4. Request arrives.
5. Middleware validates JWT.
6. Middleware extracts actor_id and tenant_id.
7. authz store loads active actor, roles, grants, permissions.
8. Handlers/services call RequirePermission and tenant/resource checks.
9. Sensitive operations write audit records.
```

So the answer is:

```
JWT is still the likely authentication mechanism.
Persisted authz actors/grants are the authorization source of truth.
The current headers are temporary compatibility scaffolding until JWT/session auth is introduced.
```
